# XD3914 使用率メーター Rev C

入力：Pico 2 H、XD3914、OSX10201-GYR1を使う概要図。
出力：CPU・GPU・NPUをそれぞれ表示する3チャンネルの試作配線図、部品表、端子表、LTspice検証。

## 1. 確定した構成

| 項目 | 設計値 |
|---|---|
| 主部品 | Pico 2 H ×1、XD3914 ×3、OSX10201-GYR1 ×3 |
| CPU出力 | GP0、Pico物理pin1 |
| GPU出力 | GP2、Pico物理pin4 |
| NPU出力 | GP4、Pico物理pin6 |
| PWM | 20kHz、各チャンネル独立 |
| 平滑回路 | 4.7kΩ 1%＋4.7µF X7R、代表時定数約22ms |
| リセット時 | 各GPIOを10kΩでGNDへプルダウン |
| 表示方式 | 10段のバー表示、走査なし |
| 基準電圧 | 各XD3914内部基準を使用。pin6とpin7を接続し、pin8をGNDへ |
| 電流設定 | pin7からGNDへ3.3kΩ 1% |
| 電源 | ドライバー基板へ安定化5V±5%、0.5A以上。PicoはUSB給電 |

CFは電圧・温度・DCバイアスを含む**実効容量が2.2～6.8µF**となる部品を選びます。公称4.7µFだけではこの範囲を保証できません。XD3914のpin3-pin2近傍に100nFと10µF、電源入口に100µFを設けます。電解コンデンサーを使う箇所は極性を守ってください。

PicoのGND（例：物理pin3）とドライバー基板GNDを共通にします。外部5VをPicoのVBUSへ直結しません。PicoのGPIOへ接続するのはPWMとGNDだけで、外部5Vは接続しません。

## 2. 1チャンネルの接続

1. Pico GPIO → RF 4.7kΩ → XD3914 pin5（SIG）。
2. GPIOからGNDへRPD 10kΩ、pin5からGNDへCF 4.7µF。
3. XD3914 pin2（GND）・pin4（RLO）・pin8（REF ADJ）→ GND。
4. pin3（V+）・pin9（MODE）→ 5V。pin9はpin3近くへ接続しバー表示に固定。
5. pin6（RHI）とpin7（REF OUT）を接続。ここから3.3kΩでGNDへ。
6. LEDのアノードpin1～10を5Vへ。各カソードは次の表でXD3914へ接続。

| 段・色 | XD3914出力pin | LEDアノードpin | LEDカソードpin |
|---|---:|---:|---:|
| 1 / A 黄緑 | 1 | 1 | 20 |
| 2 / B 黄緑 | 18 | 2 | 19 |
| 3 / C 黄緑 | 17 | 3 | 18 |
| 4 / D 黄緑 | 16 | 4 | 17 |
| 5 / E 黄緑 | 15 | 5 | 16 |
| 6 / F 黄 | 14 | 6 | 15 |
| 7 / G 黄 | 13 | 7 | 14 |
| 8 / H 黄 | 12 | 8 | 13 |
| 9 / I 赤 | 11 | 9 | 12 |
| 10 / J 赤 | 10 | 10 | 11 |

部品のPIN1印と切欠きを必ず照合します。LEDはメーカー図の上面基準です。基板裏面から見たときは左右の見え方が変わります。

## 3. LED電流と発熱

参考式は `I_LED ≈ 10 × V_REF × (1/R_SET + 1/R_LADDER)`。内部の分圧抵抗へ流れる電流も含めます。

代表値VREF=1.28V、RSET=3.3kΩ、内部抵抗12kΩでは約4.95mA/段、全30段で約148mAです。これに3個のICの動作電流と基準回路の電流が加わります。LEDごとの直列抵抗はこの定電流駆動では追加しません。

解析のストレス条件では約7.51mA/段までを確認しました。これは実部品の最大値保証ではありません。5.25V・Vfを1.8Vと仮定した保守的な手計算は、出力段約0.259W/ICに内部消費約0.025W/ICを加え、約0.285W/ICです。仕様書の55℃/Wを使う単純概算では周囲50℃で接合温度約66℃ですが、実際の基板・筐体・個体差の熱試験を代替しません。試作時は周囲0～50℃で評価し、IC温度と電流を確認してください。

## 4. 校正と表示の意味

基準電圧の個体差があるため、各ICのpin7-GND間の電圧を測定し、`firmware/control.py` の `REFERENCE_V` を3個分書き換えます。GPIOの実際のHigh電圧を測定して `GPIO_HIGH_V` も設定してください。初期値1.28V/3.30Vは代表値であり、校正済みの値ではありません。

この試作では次のように10%刻みで表示します。

- 0～9%：消灯、10～19%：1段、…、90～99%：9段、100%：10段。
- 1～9段は、対応する2つの判定電圧の中央を狙います。閾値に直接合わせず、PWMリップルによるちらつきに余裕を設けます。
- 10段は基準電圧の1.08倍を狙います。

例：基準1.28Vなら3段は0.448V、6段は0.832V、10段は1.3824V。実際はGPIOの出力抵抗・入力電流などで少し変わるため、pin5でも測定します。

## 5. 検証した内容

保存レポートにはLTspice 26.1.1で次の72件が合格した記録があります。ただし、コミット済みの両ログは保存SHA256と一致せず、現時点では証跡の再確認に失敗します。下表は過去の記録であり、現行ファイルの検証完了を意味しません。LTspice再実行が必要です。

| 試験 | 条件・確認 |
|---|---|
| PWM・リセット | 実効CF=2.2/6.8µF、20kHz、3/6/10段の独立表示 |
| 起動前 | PWM開始前50msで全段消灯 |
| リセット | 400msでGPIOを高インピーダンスへ。750ms時点で全段消灯 |
| 残留リップル | 最大約3.85mV、今回の基準6mV未満 |
| 全段階 | 0～10段 × 2ストレス条件 × 3チャンネル＝66件 |
| 配線整合 | LTspiceがASCから生成した67部品の端子リストを、設計側のリストと照合 |
| 消費電力 | 出力段＋内部電流によるIC損失概算は最大約0.265W/IC |

ストレス試験は基準電圧1.20/1.28/1.34V、RSET±1%、内部分圧抵抗8/17kΩ、比較閾値誤差±41.8mV、LED電流倍率0.7/1.3、供給5.25Vを組み合わせています。各基準電圧は校正済みとして入力を設定します。内部分圧精度などには特定の測定条件があるため、これらを単純に足したストレス値はメーカーのワーストケース保証ではありません。全公差の全組合せを網羅した試験でもありません。

モデルはバー表示、基準負荷、10比較器、定電流出力、出力電圧不足時の電流低下、100nAの入力電流を近似します。LED/GPIOも仮定モデルです。電源立上り途中の内部状態、発振、実際の温度変化、基板寄生、色ごとの明るさ、MCU実行そのものは再現していません。

## 6. 初回の組立・実機確認

1. 最初は1チャンネルだけ組み立てます。無通電で部品の向き、5V-GNDの短絡、LEDの極性を確認します。
2. Picoを外した状態で、電流制限を約0.1Aに設定できる5V電源から1チャンネルへ給電し、消灯とpin7の基準電圧を確認します。
3. PicoへMicroPythonを用意し、`control.py` と `main.py` をコピー。校正値を設定します。
4. GPIOが0Vであることを確認してから、共通GNDと信号線を接続します。作業中の配線変更は無通電で行います。
5. USBシリアルから `10,0,0`、`50,0,0`、`100,0,0` を送って1/5/10段を確認します。2秒未満の間隔で送り続けないとタイムアウト消灯します。
6. pin5の平均電圧とリップル、LED電流、5V電圧を測定します。LED電流を測る電流計は電源と並列に接続せず、測定するLEDの枝へ直列に入れます。
7. 残る2チャンネルを追加。全30段点灯時の電流・IC温度・明るさ・リセット後の消灯を確認します。

通常の通信タイムアウトや不正入力時はソフトウェアでPWM=0にします。リセットでGPIOが浮いた場合はRPD経由の放電となり、消灯まで数百msかかります。ソフトウェアが停止しPWMが走り続ける故障を、この回路だけで検知することはできません。

付属ファームウェアはUSBから数値を受けて表示する最小実装です。ロジックはホストPythonで検証済みですが、Pico実機での実行は未確認です。PC側のCPU/GPU/NPU使用率取得プログラムは含めていません。

## 7. 再生成とLTspice再実行

```powershell
node hardware/build.cjs
```

`simulation/ltspice/level_meter.asc` と `levels.cir` をLTspiceで開き、それぞれRunします。回路と同じフォルダーに2個のASYとmeter_models.libが必要です。

ログの完了・更新を確認します。通常の保存証跡チェックは、既存の `.net` の有無に関係なく次を実行します。

```powershell
node simulation/ltspice/verify-meter.cjs
```

新しい実行結果を保存する場合だけ、両試験をLTspiceで再実行し、ASCから生成された `level_meter.net` を残したまま `node simulation/ltspice/verify-meter.cjs --record-run` を実行します。入力ファイルより新しいネットリスト・ログが必要で、測定値と配線のチェックがすべて合格した場合だけJSONを更新します。更新時刻の検査は実際にLTspiceを実行した証明ではありません。古いファイルのコピーや時刻変更で代用しないでください。

`.net` はLTspiceが生成する中間ファイルです。通常チェックでは回路・モデル・ログのハッシュが保存証跡と一致する場合に限り、中間ファイル削除後も保存したネットリストで再確認できます。新しい証跡では `.net` 全文のハッシュも保存し、部品以外の解析指示の変更も検出します。従来の証跡に `.net` 全文ハッシュがない場合は、`.net` を取り除いて保存済みスナップショットを確認するか、LTspiceを再実行して記録し直します。新しい証跡はテキストの改行をLFへ正規化してハッシュ化するため、GitのLF/CRLF変換だけでは失効しません。従来形式は一致を証明できる改行違いだけを許容し、内容の不一致は失敗します。バッチ実行がログを更新しない環境ではGUIから実行し、古い結果を新しい結果として使用しないでください。

ファームウェアの計算・入力検証：`python firmware/control.py`。
